# Entrega de Banco de Dados — Sistema de Alertas Comunitários

Banco: PostgreSQL 17. Estrutura versionada por migrações Flyway em `src/main/resources/db/migration/` e exportada em `database/schema.sql`. Abaixo estão só os trechos de SQL pertinentes a cada critério.

## 1. Introdução

O Sistema de Alertas Comunitários é uma aplicação web (Java 21, Spring Boot, PostgreSQL) em que moradores de áreas de risco comunicam ocorrências e representantes de entidades públicas as verificam e avisam a comunidade. Há três perfis:

- **Administrador**: gerencia as contas dos representantes e consulta a auditoria.
- **Representante** (entidade pública): cadastra áreas de risco, residências e moradores; registra e verifica ocorrências; emite alertas; altera e encerra ocorrências, notificando os moradores que receberam alertas.
- **Morador**: acessa com CPF e senha, registra ocorrências com fotos na área da sua residência, acompanha os relatos e alertas e recupera o acesso.

Principais funcionalidades: cadastro de áreas de risco, residências e moradores; contas de representantes; autenticação com troca da senha temporária e bloqueio por tentativas; registro, consulta, verificação, alteração e encerramento de ocorrências; emissão e distribuição de alertas; auditoria das ações.

## 2. Criação das tabelas e as quatro integridades

Tabelas centrais: `areas_risco`, `residencias`, `moradores`, `ocorrencias` e `registros_auditoria`. Os comentários `[E]` entidade, `[R]` referencial, `[D]` domínio e `[S]` semântica/definida pelo usuário foram acrescentados neste documento para apontar cada integridade; os arquivos de origem não os têm.

Arquivo: `V2__criar_areas_risco.sql`

```sql
CREATE TABLE areas_risco (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,      -- [E] chave primária
    nome TEXT NOT NULL CHECK (nome ~ '[^[:space:]]'),           -- [D] obrigatório; [S] não pode ser só espaços
    descricao_localizacao_limites TEXT NOT NULL
        CHECK (descricao_localizacao_limites ~ '[^[:space:]]')
);
```

Arquivo: `V7__criar_residencias.sql`

```sql
CREATE TABLE residencias (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,                      -- [E]
    rua_logradouro TEXT NOT NULL CHECK (length(trim(rua_logradouro)) > 0),      -- [D]
    ...
    area_id BIGINT NOT NULL REFERENCES areas_risco(id) ON DELETE RESTRICT        -- [R] toda residência pertence a uma área
);
```

Arquivos: `V8__criar_moradores.sql` e `V11__controle_acesso_moradores.sql`

```sql
CREATE TABLE moradores (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,                               -- [E]
    cpf TEXT NOT NULL CHECK (cpf ~ '^[0-9]{11}$'),                                       -- [D] formato de 11 dígitos
    celular TEXT NOT NULL CHECK (celular ~ '^[0-9]{11}$'),                               -- [D]
    residencia_id BIGINT NOT NULL REFERENCES residencias(id) ON DELETE RESTRICT,         -- [R]
    canal_credenciais TEXT NOT NULL CHECK (canal_credenciais IN ('SMS', 'WHATSAPP')),    -- [D] domínio enumerado
    preferencia_alertas TEXT NOT NULL CHECK (preferencia_alertas IN ('SMS', 'WHATSAPP', 'AMBOS')),
    ativa BOOLEAN NOT NULL,
    CONSTRAINT uk_moradores_cpf UNIQUE (cpf),                                            -- [S] CPF exclusivo
    CONSTRAINT uk_moradores_celular UNIQUE (celular)                                     -- [S] telefone exclusivo
);

ALTER TABLE moradores
    ADD COLUMN troca_senha_obrigatoria BOOLEAN NOT NULL DEFAULT TRUE,                    -- [D] DEFAULT
    ADD COLUMN falhas_login INTEGER NOT NULL DEFAULT 0,
    ADD CONSTRAINT ck_moradores_falhas_login CHECK (falhas_login BETWEEN 0 AND 5);       -- [S] bloqueio após 5 falhas
```

Arquivos: `V9__criar_ocorrencias.sql`, `V13__ocorrencias_moradores.sql` e `V14__verificar_ocorrencias.sql`

```sql
CREATE TABLE ocorrencias (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,                               -- [E]
    protocolo UUID NOT NULL UNIQUE,                                                       -- [S] protocolo único
    tipo TEXT NOT NULL CHECK (tipo IN ('DESASTRE', 'OBRA', 'BARREIRA_CONTENCAO', 'OUTROS')), -- [D]
    especificacao_outros TEXT,
    area_id BIGINT NOT NULL REFERENCES areas_risco(id) ON DELETE RESTRICT,                -- [R]
    representante_id BIGINT NOT NULL REFERENCES representantes(id) ON DELETE RESTRICT,    -- [R]
    CONSTRAINT uk_ocorrencias_envio UNIQUE (representante_id, envio_id),                  -- [S] mesmo envio não duplica
    CONSTRAINT ck_ocorrencias_outros CHECK (tipo <> 'OUTROS' OR (especificacao_outros IS NOT NULL
        AND especificacao_outros ~ '[^[:space:]]'))                                       -- [S] "Outros" exige especificação
);

ALTER TABLE ocorrencias
    ALTER COLUMN representante_id DROP NOT NULL,
    ADD COLUMN morador_id BIGINT REFERENCES moradores(id) ON DELETE RESTRICT,             -- [R]
    ADD CONSTRAINT ck_ocorrencias_um_autor CHECK ((representante_id IS NULL) <> (morador_id IS NULL)); -- [S] um único autor

ALTER TABLE ocorrencias
    ADD CONSTRAINT ocorrencias_situacao_check
        CHECK (situacao IN ('EM_VERIFICACAO', 'CONFIRMADA', 'NAO_CONFIRMADA', 'ENCERRADA')); -- [D]
```

Arquivos: `V6__criar_auditoria.sql` e `V13__ocorrencias_moradores.sql`

```sql
CREATE TABLE registros_auditoria (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,                               -- [E]
    acao TEXT NOT NULL CHECK (length(trim(acao)) > 0),                                    -- [D]
    responsavel_tipo TEXT NOT NULL CHECK (responsavel_tipo IN ('ADMINISTRADOR', 'REPRESENTANTE')), -- [D]
    responsavel_id BIGINT NOT NULL CHECK (responsavel_id > 0),                            -- [S]
    ocorrido_em TIMESTAMPTZ NOT NULL
);
-- V13 amplia o domínio para ('ADMINISTRADOR', 'REPRESENTANTE', 'MORADOR').
```

Como atende: toda tabela tem chave primária (entidade); as FKs com `ON DELETE RESTRICT` impedem apagar uma área, residência ou representante ainda referenciado (referencial); tipos, `NOT NULL`, `DEFAULT` e `CHECK` de valores enumerados e formatos limitam o domínio; `UNIQUE` e `CHECK` com várias colunas impõem regras do negócio (CPF e celular exclusivos, um único autor por ocorrência, especificação obrigatória para "Outros").

## 3. Trigger

Arquivo: `V18__auditoria_imutavel.sql` (criado para esta entrega)

```sql
CREATE FUNCTION impedir_alteracao_auditoria() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    RAISE EXCEPTION 'registros_auditoria é imutável: UPDATE do registro % não é permitido', OLD.id
        USING ERRCODE = 'restrict_violation';
END
$$;

CREATE TRIGGER tg_registros_auditoria_imutavel
    BEFORE UPDATE ON registros_auditoria
    FOR EACH ROW EXECUTE FUNCTION impedir_alteracao_auditoria();
```

Como atende: o registro de auditoria (RF013) não pode ser alterado depois de gravado, nem pelo dono da tabela. Nenhum fluxo do sistema altera auditoria. A exclusão é negada pelas permissões (seção 5): a aplicação só recebe `SELECT` e `INSERT` nessa tabela.

## 4. Campo indexado

Arquivo: `V15__alertas_ocorrencias.sql` (já existia)

```sql
CREATE INDEX ix_destinatarios_morador ON destinatarios_comunicado(morador_id);
```

Como atende: a tela de alertas do morador busca os comunicados recebidos por `morador_id` (`ComunicadoRepository.doMorador`). Sem o índice, essa consulta percorreria todos os destinatários de todos os alertas. As migrações também criam `ix_verificacoes_ocorrencia`, `ix_comunicados_ocorrencia` e `ix_alteracoes_ocorrencia`; as restrições `PRIMARY KEY` e `UNIQUE` (por exemplo, `ocorrencias.protocolo`) geram índices implícitos.

## 5. Contas e permissões

Arquivo: `database/contas-permissoes.sql` (criado para esta entrega). Não é uma migração Flyway porque os papéis pertencem ao cluster. O DBA roda o script e passa as senhas por variável: `psql -d alertas -v senha_admin=... -v senha_app=... -v senha_leitura=... -f database/contas-permissoes.sql`.

```sql
CREATE ROLE alertas_admin LOGIN PASSWORD :'senha_admin';      -- dono da estrutura: DDL e migrações Flyway
CREATE ROLE alertas_app LOGIN PASSWORD :'senha_app';          -- a aplicação Spring: só DML necessário
CREATE ROLE alertas_leitura LOGIN PASSWORD :'senha_leitura';  -- consulta: só a view de resumo

REVOKE ALL ON DATABASE :"DBNAME" FROM PUBLIC;
REVOKE ALL ON SCHEMA public FROM PUBLIC;
REVOKE ALL ON ALL TABLES IN SCHEMA public FROM PUBLIC;
GRANT CONNECT ON DATABASE :"DBNAME" TO alertas_admin, alertas_app, alertas_leitura;

ALTER SCHEMA public OWNER TO alertas_admin;   -- e, em laço, ALTER TABLE ... OWNER TO alertas_admin

GRANT USAGE ON SCHEMA public TO alertas_app, alertas_leitura;
GRANT SELECT, INSERT, UPDATE ON areas_risco, residencias, moradores, representantes, administradores,
    ocorrencias, fotos_ocorrencia, comunicados_ocorrencia, destinatarios_comunicado TO alertas_app;
GRANT DELETE ON areas_risco, residencias TO alertas_app;
GRANT SELECT, INSERT ON registros_auditoria, verificacoes_ocorrencia, alteracoes_ocorrencia,
    encerramentos_ocorrencia TO alertas_app;

GRANT SELECT ON vw_resumo_ocorrencias_area TO alertas_leitura;
```

Como atende: três contas com privilégio mínimo. Primeiro o script retira tudo de `PUBLIC`. Depois a aplicação recebe só o DML que usa: só exclui áreas e residências, e os históricos (auditoria, verificações, alterações, encerramentos) aceitam apenas inclusão e consulta. A conta de leitura enxerga apenas a view, sem dados pessoais.

## 6. View

Arquivo: `V19__resumo_ocorrencias_area.sql` (criado para esta entrega)

```sql
CREATE VIEW vw_resumo_ocorrencias_area AS
SELECT a.id AS area_id,
       a.nome AS area,
       o.situacao,
       COUNT(*) AS total,
       MAX(o.registrada_em) AS ultima_registrada_em
FROM ocorrencias o
JOIN areas_risco a ON a.id = o.area_id
GROUP BY a.id, a.nome, o.situacao;
```

Como atende: resume as ocorrências por área e situação (em verificação, confirmada, não confirmada, encerrada) sem expor autor, descrição, fotos ou dados de moradores. É o único objeto liberado para `alertas_leitura`.
